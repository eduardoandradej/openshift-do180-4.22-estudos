## Parte A — Entendendo o conceito

### O problema que resolvem

Um Pod que referencia uma **tag** não tem garantia de receber a mesma imagem ao ser
recriado (7.1). Usar digests resolve a imutabilidade, mas é pouco legível e não traz
histórico. A **ImageStream** é uma **camada de abstração** do OpenShift sobre as
imagens:

- dá um **nome curto e estável** (ex.: `keycloak:25.0`), independente de registry e de configuração do runtime;
- guarda o **digest** e um **histórico** das imagens de cada tag: reprodutibilidade e **rollback**;
- isola o cluster de mudanças no registry externo;
- facilita a **promoção** de imagens entre ambientes e o **controle** de quais imagens podem ser usadas.

É um dos principais diferenciais do OpenShift em relação ao Kubernetes. Recursos do
OpenShift, como BuildConfigs, referenciam ImageStreams, e o OpenShift estende
recursos Kubernetes (Deployments) com **anotações** para usá-las.

### ImageStream e ImageStreamTag

| Objeto | Abreviação | O que é |
|--------|------------|---------|
| **ImageStream** | `is` | Conjunto de "fluxos" de imagens, com configurações padrão para as tags |
| **ImageStreamTag** | `istag` | Um fluxo: aponta para uma imagem de origem e guarda o **digest atual** e o **histórico** |

Diferenças em relação a tags de registry:

- Uma ImageStream pode ter tags que apontam para **registries e repositórios
  diferentes** (ex.: `postgresql:15-el8` e `postgresql:15-el9` vindos de repositórios distintos).
- Cada ImageStreamTag guarda uma **cópia dos metadados** da imagem, inclusive o
  digest. Consultas e inspeções não precisam ir ao registry.
- Opcionalmente, guarda as **camadas** no **registry interno** do OpenShift (cache
  local, *pull-through*).

O projeto `openshift` traz ImageStreams prontas (php, postgresql, etc.). No ambiente
de laboratório há um subconjunto delas.

### Por que isso dá reprodutibilidade

- Uma imagem nunca muda: uma "nova versão" é uma imagem com **outro digest**, e o
  registry passa a associar o mesmo nome a ela.
- A ImageStreamTag **não segue** o registry sozinha: mantém o **último digest
  importado** até você atualizá-la.
- Consequência: ao escalar dias depois, **todos** os Pods usam o **mesmo digest**,
  mesmo que o fornecedor tenha publicado outra imagem com o mesmo nome.
- O histórico (`*` marca o atual em `oc describe is`) permite voltar a uma imagem anterior.

Por padrão, o OpenShift **não monitora** registries externos e as tags novas **não**
fazem verificação periódica, a menos que você configure (`--scheduled`).

### Casos de uso

| Caso | Como a ImageStream ajuda |
|------|--------------------------|
| Trocar de registry (ex.: criar um espelho interno) | Usuários continuam usando o mesmo nome curto |
| **Promoção** dev → QA → produção | O pipeline marca o **mesmo digest** em `app:latest-dev`, `app:qa-stable`, `app:prod-v1.2`: o que foi testado é o que vai para produção |
| Trocar de fornecedor de imagem (ex.: segurança) | Aponta a tag para outra origem compatível |
| Usar imagens Red Hat endurecidas e suportadas | Substitui origens pouco confiáveis sem mudar os Deployments |

### Atualização periódica e pull-through

| Opção do `oc tag` | Efeito | Uso |
|-------------------|--------|-----|
| `--scheduled` | Verifica periodicamente a origem (padrão a cada **15 minutos**, ajustável pelo administrador) e atualiza a tag se houver imagem nova | Origens confiáveis com correções frequentes (ex.: imagens Red Hat) |
| `--reference-policy local` | **Pull-through**: na primeira vez baixa da origem e guarda no registry interno; depois, os nós baixam do registry interno | Registries lentos, com limite de banda, ou para resistir a quedas da internet |

### Usar ImageStreams em Deployments (e Jobs, CronJobs, Pods)

Três requisitos:

1. A ImageStream no **mesmo projeto** do Deployment.
2. **Local lookup policy** habilitada na ImageStream (`oc set image-lookup`).
3. O Deployment referencia a tag pelo **nome curto** (`keycloak:25.0`), não pelo nome completo do registry.

Ao ver um nome curto, o OpenShift procura uma ImageStream com lookup local habilitado
no projeto. Se não encontrar, trata o nome como imagem comum dos registries
permitidos.

A ImageStreamTag funciona como uma **tag com memória**: aponta para um digest
congelado, lembra os anteriores e só muda quando você manda.

## Parte C — Funcionamento na prática

### Explorar

```bash
oc get is -n openshift -o name
oc get istag -n openshift | grep postgresql
oc describe is postgresql -n openshift      # tags, origem, digest atual (*), histórico
oc get is keycloak -o yaml                  # spec.tags (desejado) × status.tags (histórico de digests)
```

Campos do YAML que importam:

| Campo | Significado |
|-------|-------------|
| `spec.lookupPolicy.local` | Se a ImageStream atende nomes curtos no projeto |
| `spec.tags[].from` | Origem da tag (`kind: DockerImage`, `name: quay.io/...`) |
| `spec.tags[].importPolicy` / `referencePolicy` | Importação agendada; `Source` ou `Local` (pull-through) |
| `status.dockerImageRepository` | Caminho da ImageStream no registry interno |
| `status.tags[].items[]` | Histórico: `dockerImageReference` com o **digest**, `created` |

### Criar ImageStreams e tags

```bash
oc create is keycloak                                              # ImageStream vazia
oc import-image keycloak:25.0 --from=quay.io/keycloak/keycloak:25.0.2 --confirm
oc tag quay.io/keycloak/keycloak:19.0 keycloak:19.0                # cria a IS se não existir
oc create istag keycloak:26.6 --from-image quay.io/keycloak/keycloak:26.6   # só criação inicial
```

| Comando | Cria | Atualiza tag existente |
|---------|------|------------------------|
| `oc import-image <is:tag> --from <img> --confirm` | ✅ (inclusive a IS) | ✅ (reexecutar reimporta) |
| `oc tag <img> <is:tag>` | ✅ | ✅ |
| `oc create istag <is:tag> --from-image <img>` | ✅ | ❌ |

### Atualizar, agendar e fazer cache

```bash
oc tag quay.io/keycloak/keycloak:25.0.4 keycloak:25.0                  # nova origem para a tag
oc describe is keycloak                                                # novo * e histórico
oc tag quay.io/keycloak/keycloak:25.0.3 keycloak:25.0 --scheduled      # verificação periódica
oc tag quay.io/keycloak/keycloak:25.0.3 keycloak:25.0 --reference-policy local   # pull-through
```

### Usar no Deployment

```bash
oc set image-lookup keycloak                  # habilita lookup local
oc set image-lookup                           # lista IS do projeto e coluna LOCAL
oc create deployment mykeycloak --image keycloak:25.0
oc get pod -l app=mykeycloak -o jsonpath='{.items[0].spec.containers[0].image}{"\n"}'
#   mostra a referência resolvida (registry + digest)
oc set image-lookup keycloak --enabled=false  # desabilitar
```

O mesmo vale para `oc create job`, `oc create cronjob` e `oc run` com `--image <is:tag>`.

**Erro comum:** sem `image-lookup`, o nome curto `keycloak:25.0` é tratado como imagem
de registry e o Pod cai em `ImagePullBackOff`.

## Parte D — Relações importantes

| A | B | Diferença essencial |
|---|---|--------------------|
| Tag de registry | ImageStreamTag | Rótulo mutável no registry × ponteiro para digest com histórico, no OpenShift |
| ImageStream | ImageStreamTag | Conjunto e padrões × um fluxo de imagens |
| `oc import-image` / `oc tag` | `oc create istag` | Cria e atualiza × só cria |
| Sem `--scheduled` | `--scheduled` | Muda só quando você manda × verifica a cada 15 min |
| `referencePolicy: Source` | `Local` (pull-through) | Nós baixam da origem × do registry interno (cache) |
| Nome curto com lookup | Nome completo | Resolvido para o digest da istag × resolvido pelo registry |
| `spec.tags` | `status.tags` | O que você configurou × o que foi importado (digests) |

## Parte F — Fixação

1. Por que um Deployment que usa `app:1.0` de uma ImageStream é mais reproduzível que um que usa `quay.io/org/app:1.0`?
2. O fornecedor publicou uma nova imagem com a mesma tag. Sua ImageStreamTag muda sozinha?
3. Um Deployment com `--image web:2.1` cai em `ImagePullBackOff`, mas a ImageStream `web` existe no projeto. O que falta?
4. Explique como ImageStreamTags apoiam a promoção dev → QA → produção.
5. Quando usar `--reference-policy local`?

<details>
<summary>Respostas comentadas</summary>

1. A ImageStreamTag guarda o digest importado: todos os Pods, mesmo criados depois, usam a mesma imagem, e há histórico para rollback. A tag de registry pode mudar a qualquer momento.
2. Não, a menos que a tag tenha `--scheduled`. Por padrão ela mantém o último digest importado até ser atualizada manualmente.
3. Habilitar o lookup local: `oc set image-lookup web`.
4. O pipeline marca o mesmo digest em tags de cada ambiente (ex.: `latest-dev`, `qa-stable`, `prod-v1.2`); o artefato testado é exatamente o que chega à produção, com rastreabilidade.
5. Quando o registry de origem é lento, tem limite de banda ou pode ficar indisponível: o registry interno passa a servir as camadas aos nós.

</details>

## Parte G — Essencial para memorizar

- ImageStream (`is`) + ImageStreamTag (`istag`) = nome curto estável + digest + histórico.
- Não segue o registry sozinha; `--scheduled` verifica a cada 15 min (padrão).
- `oc import-image is:tag --from img --confirm` · `oc tag img is:tag` · `oc create istag` (só cria).
- `--reference-policy local` = pull-through via registry interno.
- Para Deployments: mesmo projeto + `oc set image-lookup <is>` + nome curto.
- `oc describe is`: `*` marca o digest atual.
